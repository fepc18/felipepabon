El agente que nadie controla

Dale a Claude Code acceso a tu repositorio, dile "implementa el módulo de pagos" y espera. Lo más probable es que lo haga. Pero también es probable que reescriba archivos que no debía tocar, que omita los tests porque nadie se los exigió, que use una librería que ya estaba deprecada en tu proyecto, o que genere código que funciona en su cabeza pero no en tu pipeline de CI.

El problema no es el agente. El problema es que lo soltaste sin un harness.

Un agente de desarrollo sin estructura es como un desarrollador brillante en su primer día: talentoso, rápido, y completamente capaz de romper producción si nadie le explica las reglas del juego.

The agent nobody controls

Give Claude Code access to your repository, tell it "implement the payments module," and wait. Chances are it'll do it. But it might also rewrite files it shouldn't have touched, skip tests because nobody demanded them, use a library that's already deprecated in your project, or generate code that works in its own reasoning but breaks your CI pipeline.

The problem isn't the agent. The problem is you let it loose without a harness.

An unstructured coding agent is like a brilliant developer on their first day: talented, fast, and fully capable of breaking production if nobody explains the rules of the game.

Qué es Harness Engineering

Harness Engineering es la disciplina de envolver a tu agente de IA con una capa de estructura que define cómo trabaja, detecta cuándo se desvía, verifica antes de producción y entrega outputs controlados.

No se trata de limitar al agente — se trata de hacerlo confiable. La diferencia entre un agente que "a veces funciona bien" y uno en el que puedes delegar trabajo real es, precisamente, el harness.

What is Harness Engineering

Harness Engineering is the discipline of wrapping your AI agent with a layer of structure that defines how it works, detects when it deviates, verifies before production, and delivers controlled outputs.

It's not about limiting the agent — it's about making it reliable. The difference between an agent that "sometimes works well" and one you can actually delegate real work to is, precisely, the harness.

Running example

A team has this ticket: "Implement POST /payments — create a payment with amount and currency validation." They're going to delegate it to Claude Code. Let's see how the harness acts at each stage.

Guides: el CLAUDE.md como contrato de trabajo

El componente Guides define cómo trabaja el agente antes de que ejecute su primer comando. En Claude Code, este rol lo cumple el archivo CLAUDE.md — un archivo de instrucciones que el agente lee al inicio de cada sesión.

Un CLAUDE.md bien diseñado no es un README. Es un contrato. Le dice al agente qué puede tocar y qué no, qué convenciones usa el proyecto, qué tests debe correr antes de hacer commit, y cuál es la estructura de carpetas esperada.

Guides: CLAUDE.md as a work contract

The Guides component defines how the agent works before it runs its first command. In Claude Code, this role belongs to the CLAUDE.md file — an instruction file the agent reads at the start of every session.

A well-designed CLAUDE.md is not a README. It's a contract. It tells the agent what it can touch and what it can't, what conventions the project uses, what tests must pass before committing, and what the expected folder structure looks like.

Un agente sin CLAUDE.md es como un desarrollador sin onboarding: adivina las reglas del proyecto, y a veces adivina mal.
An agent without CLAUDE.md is like a developer without onboarding: it guesses the project rules, and sometimes guesses wrong.

Un buen Guide para un agente de desarrollo incluye: el stack tecnológico y las versiones exactas en uso, los comandos para correr tests y linting, las carpetas que nunca debe modificar (como /migrations o configs de infraestructura), y el estilo de commits que esperas. También puedes indicarle cuándo debe detenerse a preguntar en lugar de decidir solo — por ejemplo, antes de eliminar cualquier archivo o antes de cambiar la firma de una función pública.

A good Guide for a coding agent includes: the tech stack and exact versions in use, commands to run tests and linting, folders it should never modify (like /migrations or infrastructure configs), and the commit style you expect. You can also tell it when to stop and ask rather than decide alone — for example, before deleting any file or before changing a public function's signature.

Ejemplo — CLAUDE.md

Antes de recibir el ticket de pagos, el agente lee este contrato:

## Stack
Node 20 · Express 4 · PostgreSQL 15 · Jest

## Carpetas protegidas — nunca modificar
/migrations   → cambios de DB requieren aprobación
/infra        → configuración de infraestructura
.env*         → nunca tocar variables de entorno

## Antes de cada commit
npm test && npm run lint
Si alguno falla → corrígelo antes de continuar.

## Convenciones
- Rutas en src/routes/, lógica en src/services/
- Tests en __tests__/ junto al archivo que prueban
- Commits: feat|fix|test|refactor: descripción corta

## Cuándo detenerse a preguntar
- Antes de eliminar cualquier archivo
- Antes de cambiar la firma de una función pública
- Si el ticket requiere cambio de esquema de DB

Con este contrato cargado, el agente sabe exactamente dónde implementar el endpoint (src/routes/), dónde poner la lógica (src/services/), y que si necesita un cambio de DB debe parar y preguntar.

Before receiving the payments ticket, the agent reads this contract:

Sensors: hooks que detectan desviaciones

Los Sensors son el sistema nervioso del harness. En Claude Code, se implementan mediante hooks — scripts que se ejecutan automáticamente antes o después de cada herramienta que usa el agente.

Claude Code soporta 4 tipos de hooks: PreToolUse (antes de ejecutar una herramienta), PostToolUse (después), Notification (cuando el agente quiere notificar algo) y Stop (cuando el agente termina). Los más útiles para un harness de desarrollo son los dos primeros.

Sensors: hooks that detect deviations

Sensors are the harness's nervous system. In Claude Code, they're implemented via hooks — scripts that run automatically before or after each tool the agent uses.

Claude Code supports 4 hook types: PreToolUse (before a tool runs), PostToolUse (after), Notification (when the agent wants to notify something), and Stop (when the agent finishes). The most useful for a coding harness are the first two.

Un sensor típico para un agente de desarrollo puede verificar: que el agente no ejecute comandos destructivos sin confirmación, que no escriba sobre archivos de configuración de infraestructura, que no instale dependencias fuera del package manager del proyecto, o que no haga push directamente a main. Estos controles parecen obvios — pero sin hooks, dependen de que el agente "recuerde" las instrucciones del CLAUDE.md en cada paso.

Los hooks en Claude Code se configuran en .claude/settings.json o via claude settings, y pueden ser scripts de bash, Python, o cualquier ejecutable. El hook recibe como stdin un JSON con el nombre de la herramienta y sus argumentos, y puede retornar un código de salida distinto de 0 para bloquear la ejecución.

A typical sensor for a coding agent might check: that the agent doesn't run destructive commands without confirmation, that it doesn't write to infrastructure config files, that it doesn't install dependencies outside the project's package manager, or that it doesn't push directly to main. These checks seem obvious — but without hooks, they rely on the agent "remembering" the CLAUDE.md instructions at every step.

Hooks in Claude Code are configured in .claude/settings.json or via claude settings, and can be bash scripts, Python, or any executable. The hook receives a JSON with the tool name and its arguments via stdin, and can return a non-zero exit code to block execution.

Ejemplo — Sensor en acción

El agente está implementando POST /payments y decide que necesita una nueva columna en la tabla payments. Sin preguntar, intenta crear un archivo en /migrations/. El hook PreToolUse intercepta:

# Hook recibe este payload via stdin:
{
  "tool_name": "Write",
  "tool_input": {
    "file_path": "/migrations/20260713_add_currency.sql",
    "content": "ALTER TABLE payments ADD COLUMN currency VARCHAR(3)..."
  }
}

# guard.py detecta la ruta protegida → exit(1)
BLOCKED: /migrations/ es una ruta protegida.
Los cambios de esquema requieren aprobación humana.
Crea un script en /scripts/pending-migrations/ y
abre un comentario en el PR para revisión.

El agente recibe el mensaje de bloqueo, lo incorpora como contexto, y en lugar de crear la migración procede a implementar el endpoint asumiendo que la columna ya existe — y agrega una nota en su PR summary indicando que se requiere una migración pendiente.

Example — Sensor in action

The agent receives the block message, incorporates it as context, and instead of creating the migration it proceeds to implement the endpoint assuming the column already exists — and adds a note in its PR summary flagging the pending migration.

Sandbox: verificar antes de que llegue a producción

El Sandbox es el entorno de verificación donde el código del agente debe sobrevivir antes de poder considerarse output válido. Para un agente de desarrollo, el sandbox mínimo incluye: correr los tests unitarios, pasar el linter, y compilar el proyecto sin errores.

Lo poderoso del sandbox en este contexto es que el agente puede ejecutarlo solo. Claude Code puede correr npm test, leer el output, identificar qué test falló, corregirlo, y volver a correr — sin intervención humana. El sandbox convierte al agente en un loop de feedback autónomo.

Un buen harness define explícitamente en el CLAUDE.md cuáles son los comandos del sandbox y cuándo deben ejecutarse: "antes de cada commit, corre make test y make lint. Si alguno falla, corrígelo antes de continuar." Esa instrucción, combinada con un hook PostToolUse que verifica el estado del repo, hace que el agente rara vez entregue código roto.

Sandbox: verify before it reaches production

The Sandbox is the verification environment where the agent's code must survive before it can be considered valid output. For a coding agent, the minimum sandbox includes: running unit tests, passing the linter, and compiling the project without errors.

The powerful thing about the sandbox in this context is that the agent can run it on its own. Claude Code can run npm test, read the output, identify which test failed, fix it, and re-run — without human intervention. The sandbox turns the agent into an autonomous feedback loop.

A good harness explicitly defines in CLAUDE.md what the sandbox commands are and when to run them: "before each commit, run make test and make lint. If either fails, fix it before continuing." That instruction, combined with a PostToolUse hook that checks repo state, means the agent rarely delivers broken code.

Ejemplo — Loop de autocorrección

El agente termina de implementar el endpoint y, según las instrucciones del CLAUDE.md, corre npm test antes de hacer commit:

$ npm test

  POST /payments
    ✗ should reject negative amounts (12ms)
      Expected 400, received 201
    ✓ should create payment with valid data (8ms)
    ✓ should require currency field (5ms)

  2 passing, 1 failing

El agente lee el output, identifica que falta validación de monto negativo, edita src/services/paymentsService.js, y vuelve a correr los tests:

$ npm test

  POST /payments
    ✓ should reject negative amounts (9ms)
    ✓ should create payment with valid data (8ms)
    ✓ should require currency field (5ms)

  3 passing

Sin intervención humana. El agente detectó el fallo, lo corrigió, y verificó la corrección — todo dentro del sandbox.

Output: el resultado debe ser auditable

El Output no es solo "el código que produce el agente". Es la forma en que ese código entra al sistema de control del equipo. Un output bien diseñado dentro del harness siempre es revisable, atribuible y reversible.

En la práctica, esto significa que el agente trabaja en branches, hace commits atómicos con mensajes descriptivos, y genera un Pull Request con un resumen de lo que hizo y por qué. El equipo puede revisar, aprobar o rechazar — y si algo salió mal, el diff es claro.

Un patrón que funciona bien es pedirle al agente que termine cada sesión con un resumen estructurado: qué archivos modificó, qué tests añadió, qué decisiones tomó y cuáles decisiones dejó pendientes para revisión humana. Eso convierte al agente en un colaborador explicable, no en una caja negra.

Output: the result must be auditable

Output isn't just "the code the agent produces." It's how that code enters the team's control system. Well-designed output within the harness is always reviewable, attributable, and reversible.

In practice, this means the agent works on branches, makes atomic commits with descriptive messages, and generates a Pull Request with a summary of what it did and why. The team can review, approve, or reject — and if something went wrong, the diff is clear.

A pattern that works well is asking the agent to end each session with a structured summary: what files it modified, what tests it added, what decisions it made, and which decisions it left pending for human review. That turns the agent into an explainable collaborator, not a black box.

Ejemplo — El PR que genera el agente

Con los tests en verde, el agente hace commit en su branch y abre el PR con este resumen estructurado:

Un harness completo en la práctica

Poner los 4 componentes juntos no requiere infraestructura compleja. Un harness mínimo pero efectivo para un agente de desarrollo con Claude Code puede verse así:

En el repositorio, un CLAUDE.md en la raíz define las reglas: stack, convenciones, comandos de test, carpetas protegidas y protocolo de commits. En .claude/settings.json, dos hooks: un PreToolUse que verifica comandos de escritura contra una lista de rutas protegidas, y un PostToolUse que verifica que los tests sigan pasando después de cualquier cambio. El agente trabaja siempre en un branch y abre un PR al terminar. El equipo revisa el PR en el pipeline de CI.

Con eso, el agente puede trabajar de forma autónoma en tickets de complejidad media — implementar features, corregir bugs, añadir tests, refactorizar módulos — con una tasa de output válido significativamente mayor que sin harness, y con la tranquilidad de que lo que produce puede revisarse y revertirse.

A complete harness in practice

Putting the 4 components together doesn't require complex infrastructure. A minimal but effective harness for a coding agent with Claude Code can look like this:

In the repository, a CLAUDE.md at the root defines the rules: stack, conventions, test commands, protected folders, and commit protocol. In .claude/settings.json, two hooks: a PreToolUse that checks write commands against a list of protected paths, and a PostToolUse that verifies tests still pass after any change. The agent always works on a branch and opens a PR when done. The team reviews the PR in the CI pipeline.

With that, the agent can work autonomously on medium-complexity tickets — implementing features, fixing bugs, adding tests, refactoring modules — with a significantly higher rate of valid output than without a harness, and with the peace of mind that what it produces can be reviewed and reverted.

El harness no limita al agente — lo hace confiable

La tentación cuando se trabaja con agentes de código es ir rápido: darle acceso total, pedirle la feature, y ver qué produce. A veces funciona. Pero a medida que la base de código crece, el equipo escala, o los stakes aumentan, ese enfoque se vuelve frágil.

Harness Engineering no es burocracia — es lo que permite que delegar trabajo a un agente se convierta en una práctica sostenible. Un agente con un buen harness no solo produce mejor código: produce código en el que el equipo puede confiar, auditar y evolucionar.

La ingeniería de IA no termina en el modelo. Termina en el sistema que lo rodea.

The harness doesn't limit the agent — it makes it reliable

The temptation when working with coding agents is to move fast: give it full access, ask for the feature, and see what it produces. Sometimes it works. But as the codebase grows, the team scales, or the stakes increase, that approach becomes fragile.

Harness Engineering isn't bureaucracy — it's what allows delegating work to an agent to become a sustainable practice. An agent with a good harness doesn't just produce better code: it produces code the team can trust, audit, and evolve.

AI engineering doesn't end at the model. It ends at the system surrounding it.
