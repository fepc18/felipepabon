50 System Design Concepts Every Architect Should Know

A reference guide with practical trade-offs for each concept — from scalability to RAG.

August 2026 Felipe Pabón

En system design, conocer el nombre de un concepto no es suficiente. Lo que importa es entender por qué existe y cuál es su trade-off real. Este artículo es una guía de referencia rápida de los 50 conceptos más importantes, organizados en cinco categorías, con énfasis en sus implicaciones prácticas.

In system design, knowing the name of a concept is not enough. What matters is understanding why it exists and what its real trade-off is. This article is a quick reference guide for the 50 most important concepts, organized into five categories, with emphasis on their practical implications.

1. Infraestructura Core

Los primeros diez conceptos describen cómo el tráfico fluye a través de tu sistema y cómo este crece ante la demanda.

1. Core Infrastructure

The first ten concepts describe how traffic flows through your system and how it grows under demand.

1. Scalability

La capacidad del sistema para manejar crecimiento en usuarios, datos o requests manteniendo rendimiento aceptable. El sistema es tan escalable como su componente menos escalable.

Escalar una parte sin las demás crea nuevos cuellos de botella.

2. Vertical Scaling (Scale Up)

Agregar más poder a una sola máquina: más CPU, más RAM, más almacenamiento. Simple de implementar pero tiene un límite físico y de costo.

Máquinas más grandes cuestan exponencialmente más y representan un único punto de fallo.

3. Horizontal Scaling (Scale Out)

Agregar más máquinas para distribuir la carga. Requiere que los servidores sean stateless para que cualquier instancia pueda responder cualquier request sin dependencia de sesión.

Mayor complejidad operacional: necesitas un load balancer y gestión de estado externo.

4. Load Balancer

Distribuye los requests entrantes entre múltiples servidores, redirigiendo automáticamente el tráfico alrededor de instancias caídas. Es transparente para el cliente.

El load balancer mismo puede convertirse en un punto único de fallo si no está replicado.

5. Latency

El tiempo que experimenta un usuario individual desde que envía un request hasta que recibe la respuesta. Múltiples fuentes se suman: red, procesamiento del servidor, queries a la BD.

Optimizar solo el promedio deja a los peores usuarios (p99) invisibles y desatendidos.

6. Throughput

El trabajo total completado por unidad de tiempo (requests/segundo). Distinto a latency: requests individuales rápidos no garantizan alto throughput si se procesan secuencialmente.

Aumentar throughput con concurrencia introduce complejidad de sincronización y race conditions.

7. CDN (Content Delivery Network)

Red de servidores distribuidos globalmente que cachea contenido estático cerca de los usuarios. Reduce dramáticamente la latencia para imágenes, videos y scripts.

Introduce riesgo de staleness: el contenido puede quedar desactualizado si la invalidación no está bien configurada.

8. DNS (Domain Name System)

Traduce nombres de dominio a direcciones IP. Se usa para routing de tráfico por geografía o salud del servidor mediante GeoDNS o DNS failover automático.

El cacheo DNS retrasa la propagación de cambios; un TTL bajo aumenta la carga en los servidores DNS.

9. API Gateway

Punto de entrada único que maneja autenticación, rate limiting, SSL y routing antes de que los requests lleguen a los servicios backend. Centraliza las preocupaciones transversales.

Se convierte en un componente crítico; si falla, todo el sistema deja de ser accesible desde el exterior.

10. Reverse Proxy

Recibe requests en nombre de los servidores, manejando cacheo, compresión, SSL y balanceo de carga. Los load balancers son reverse proxies especializados.

Agrega un hop extra en la red; debe ser de alta disponibilidad para no ser él mismo el cuello de botella.

1. Scalability

The ability of a system to handle growth in users, data, or requests while maintaining acceptable performance. The system is only as scalable as its least scalable part.

Scaling one component without the others creates new bottlenecks elsewhere.

2. Vertical Scaling (Scale Up)

Adding more power to a single machine: more CPU, RAM, or storage. Simple to implement but has a physical and cost ceiling.

Larger machines cost exponentially more and represent a single point of failure.

3. Horizontal Scaling (Scale Out)

Adding more machines to distribute load. Requires stateless servers so any instance can handle any request without session dependency.

Greater operational complexity: you need a load balancer and external state management.

4. Load Balancer

Distributes incoming requests across multiple servers, automatically routing around failed instances. Appears transparent to clients while managing traffic internally.

The load balancer itself can become a single point of failure if not replicated.

5. Latency

The delay experienced by an individual user from request to response. Multiple sources stack: network travel, server processing, database queries.

Optimizing only the average leaves p99 users invisible and underserved.

6. Throughput

Total work completed per unit of time (requests/second). Distinct from latency — fast individual requests don't guarantee high throughput if processed sequentially.

Increasing throughput with concurrency introduces synchronization complexity and race conditions.

7. CDN (Content Delivery Network)

Globally distributed servers caching static content near users. Dramatically reduces latency for images, videos, and scripts.

Introduces staleness risk: content can become outdated if cache invalidation is not properly configured.

8. DNS (Domain Name System)

Translates domain names to IP addresses. Used for traffic routing by geography or server health through GeoDNS or automatic DNS failover.

DNS caching delays propagation of changes; low TTL increases load on DNS servers.

9. API Gateway

Single entry point handling authentication, rate limiting, SSL, and routing before requests reach backend services. Centralizes cross-cutting concerns.

Becomes a critical component — if it fails, the entire system becomes unreachable from the outside.

10. Reverse Proxy

Receives requests on behalf of servers, handling caching, compression, SSL, and load balancing. Load balancers are specialized reverse proxies.

Adds an extra network hop; must be highly available to avoid becoming a bottleneck itself.

2. Datos y Almacenamiento

Quince conceptos que determinan cómo tu sistema persiste, accede y organiza los datos a escala.

2. Data & Storage

Fifteen concepts that determine how your system persists, accesses, and organizes data at scale.

11. Database

Sistema de almacenamiento persistente que permite recuperar datos más allá del ciclo de vida de un solo request. La elección de la BD impacta significativamente la arquitectura global.

No existe una BD "universal"; cada tipo optimiza para ciertos patrones de acceso sacrificando otros.

12. SQL Database

Bases de datos relacionales con tablas estructuradas y garantías ACID. Ideales para datos estructurados y transacciones complejas. Lenguaje de consulta maduro y estandarizado (SQL).

Escalar escrituras más allá de un solo servidor requiere sharding, que aumenta la complejidad considerablemente.

13. NoSQL Database

Categoría amplia: key-value, document, wide-column y graph stores. Cada uno optimiza para ventajas específicas de escala o flexibilidad sobre las garantías de consistencia de SQL.

La flexibilidad de esquema facilita el inicio rápido pero puede generar inconsistencias de datos a largo plazo.

14. ACID

Atomicidad (todo o nada), Consistencia (transiciones de estado válidas), Aislamiento (transacciones concurrentes independientes) y Durabilidad (sobreviven crashes). Crítico para sistemas financieros.

Las garantías ACID requieren coordination y locks, limitando el throughput en sistemas de alta concurrencia.

15. Index

Estructura de datos separada que permite búsquedas rápidas. Sin índices, las consultas escanean toda la tabla. Con índices, el motor va directo al dato en tiempo O(log n).

Los índices aceleran lecturas pero ralentizan escrituras, ya que deben mantenerse actualizados en cada modificación.

16. Sharding

División de datos entre múltiples bases de datos por una shard key. Escala las escrituras y el almacenamiento cuando una sola BD no alcanza. Popular en sistemas de gran escala como Twitter o Stripe.

Una shard key mal elegida crea hot partitions. Las queries cross-shard son costosas y complejas de implementar.

17. Replication

Mantener copias de datos en múltiples máquinas, típicamente mediante un modelo leader-follower. Permite escalar lecturas distribuyendo queries entre réplicas. Mejora también la resiliencia ante fallos.

Introduce replication lag: las réplicas pueden tener datos brevemente desactualizados respecto al leader.

18. Cache

Almacenamiento rápido en memoria que guarda copias de datos frecuentemente accedidos. Reduce dramáticamente la latencia y la carga en la base de datos primaria. Ejemplos: Redis, Memcached.

Los datos pueden quedar stale cuando cambia la fuente original. Requiere estrategias de expiración e invalidación deliberadas.

19. Cache-Aside

La aplicación revisa el cache primero; si hay miss, busca en la BD y almacena el resultado en cache. Población lazy con degradación graceful si el cache falla.

Cache misses son caros (dos operaciones: BD + escritura en cache). Los primeros requests siempre son lentos (cold start).

20. Write-Through

Cada escritura va simultáneamente al cache y a la BD. Garantiza consistencia entre ambas capas; el cache siempre refleja el estado actual de la BD.

Aumenta la latencia de escritura ya que ambas operaciones deben completarse antes de confirmar al cliente.

21. Write-Behind

Las escrituras se confirman inmediatamente al cache y luego se sincronizan asincrónicamente con la BD. Escrituras ultrarrápidas desde la perspectiva del cliente.

Riesgo de pérdida de datos: si el cache falla antes de sincronizar con la BD, las escrituras pendientes se pierden.

22. Consistent Hashing

Distribuye datos entre nodos minimizando la redistribución al escalar. Agregar un nodo a diez requiere mover ~10% de los datos, no ~90% como con hashing tradicional.

La distribución puede ser desigual sin virtual nodes. Implementación más compleja que hashing estándar.

23. Object Storage

Sistema infinitamente escalable para archivos no estructurados (imágenes, videos, documentos). Barato y durable. Ejemplos: Amazon S3, Google Cloud Storage.

Inadecuado para bases de datos que requieren transacciones o acceso aleatorio de baja latencia.

24. Data Partitioning

División de datos en unidades de almacenamiento separadas por criterios como ID, rango de fechas o región geográfica. Mejora el rendimiento reduciendo los datos escaneados por query.

Una partición incorrecta puede resultar en full-table scans o particiones desbalanceadas con hot spots de acceso.

25. Event Sourcing

Almacena secuencias de eventos que producen el estado, en lugar del estado actual. Habilita auditoría completa y queries de "time-travel". Muy útil en sistemas financieros y de compliance.

Reproducir eventos para obtener el estado actual es lento sin snapshots periódicos. El event store crece indefinidamente.

11. Database

Persistent storage system enabling data retrieval beyond a single request lifecycle. The choice of database significantly impacts the overall architecture.

No "universal" database exists; each type optimizes for certain access patterns at the expense of others.

12. SQL Database

Relational databases with structured tables and ACID guarantees. Ideal for structured data and complex transactions. Their query language is mature and standardized (SQL).

Scaling writes beyond a single server requires sharding, which adds considerable complexity.

13. NoSQL Database

Broad category: key-value, document, wide-column, and graph stores. Each optimizes for specific scale or flexibility advantages over SQL's consistency guarantees.

Schema flexibility speeds up early development but can create data inconsistencies over time.

14. ACID

Atomicity (all-or-nothing), Consistency (valid state transitions), Isolation (concurrent transactions are independent), Durability (data survives crashes). Critical for financial systems.

ACID guarantees require coordination and locks, limiting throughput in high-concurrency systems.

15. Index

A separate data structure enabling fast query lookup. Without indexes, queries scan the full table. With indexes, the engine jumps to the data in O(log n) time.

Indexes speed up reads but slow down writes, since they must be maintained on every modification.

16. Sharding

Splitting data across multiple databases by a shard key. Scales writes and storage when a single DB can't keep up. Common in large-scale systems like Twitter or Stripe.

A poorly chosen shard key creates hot partitions. Cross-shard queries are expensive and complex to implement.

17. Replication

Keeping data copies across multiple machines, typically via a leader-follower model. Scales reads by distributing queries among replicas. Also improves resilience to failures.

Introduces replication lag: replicas may briefly have stale data compared to the leader.

18. Cache

Fast in-memory storage holding copies of frequently accessed data. Dramatically reduces latency and load on the primary database. Examples: Redis, Memcached.

Data can become stale when the source changes. Requires intentional expiry and invalidation strategies.

19. Cache-Aside

The application checks cache first; on a miss, fetches from DB and stores the result in cache. Lazy population with graceful degradation if cache fails.

Cache misses are expensive (two operations: DB read + cache write). First requests are always slow (cold start).

20. Write-Through

Every write goes simultaneously to cache and DB. Guarantees consistency between both layers; the cache always reflects the current DB state.

Increases write latency since both operations must complete before confirming to the client.

21. Write-Behind

Writes are immediately acknowledged to cache, then asynchronously synced to DB. Ultra-fast writes from the client's perspective.

Risk of data loss: if the cache fails before syncing with the DB, pending writes are lost.

22. Consistent Hashing

Distributes data across nodes minimizing reshuffling when scaling. Adding one node to ten requires moving ~10% of data, not ~90% as with traditional hashing.

Distribution can be uneven without virtual nodes. More complex to implement than standard hashing.

23. Object Storage

Infinitely scalable system for unstructured files (images, videos, documents). Cheap and durable. Examples: Amazon S3, Google Cloud Storage.

Unsuitable for databases requiring transactions or low-latency random access.

24. Data Partitioning

Dividing data into separate storage units by ID range, date, or region. Improves query performance by reducing the amount of data scanned per query.

Wrong partitioning can result in full-table scans or unbalanced partitions with access hot spots.

25. Event Sourcing

Stores sequences of events producing state instead of the current state. Enables complete audit trails and time-travel queries. Very useful in financial and compliance systems.

Replaying events to get the current state is slow without periodic snapshots. The event store grows indefinitely.

3. Sistemas Distribuidos

Trece conceptos que abordan los desafíos fundamentales cuando múltiples máquinas deben coordinarse: fallos parciales, consistencia y consenso.

3. Distributed Systems

Thirteen concepts addressing the fundamental challenges when multiple machines must coordinate: partial failures, consistency, and consensus.

26. Distributed System

Múltiples máquinas comunicándose por red para lograr objetivos compartidos. Introduce desafíos únicos: fallos de red, fallos parciales y consistencia entre copias de datos.

Los sistemas distribuidos traen complejidad que los monolitos no tienen; justifícalos con necesidad real de escala.

27. CAP Theorem

Un sistema distribuido puede garantizar solo dos de tres propiedades: Consistency, Availability, Partition tolerance. Como las particiones son inevitables, la elección real durante fallos es entre C o A.

No existe un sistema que sea 100% consistente Y 100% disponible ante particiones de red simultáneas.

28. Strong Consistency

Cada lectura refleja la última escritura sin importar qué nodo responde. Requiere coordinación entre nodos antes de responder. Apropiado para datos financieros e inventario crítico.

El overhead de coordinación reduce throughput y aumenta latencia en comparación con eventual consistency.

29. Eventual Consistency

Las réplicas convergen al mismo estado con el tiempo pero pueden diferir brevemente. Más barato y más disponible. Adecuado para contadores de likes, feeds y recomendaciones.

Los clientes pueden leer datos stale temporalmente; inaceptable para sistemas donde la precisión es crítica.

30. Consensus

Múltiples nodos acuerdan un único valor a pesar de fallos individuales. Algoritmos como Raft y Paxos requieren acuerdo de la mayoría, previniendo escenarios split-brain.

El consenso es costoso en latencia y tráfico de red; se usa selectivamente para decisiones críticas.

31. Leader Election

Nodos distribuidos acuerdan cuál coordina el trabajo. Requiere consenso para prevenir líderes duales. Usado en bases de datos distribuidas como etcd o coordinadores de tareas.

La ventana de tiempo entre que un líder falla y uno nuevo se elige reduce temporalmente la capacidad del sistema.

32. Idempotency

Operaciones que producen el mismo resultado si se ejecutan una o múltiples veces. Los sistemas distribuidos no pueden garantizar entrega exactamente-una-vez, haciendo esto esencial para retries seguros.

Implementar idempotencia requiere rastrear operaciones ya ejecutadas, lo que añade overhead de estado y storage.

33. Idempotency Key

Identificador único generado por el cliente que permite al servidor detectar y rechazar requests duplicados. Estándar en APIs de pago (Stripe, PayPal) para prevenir cobros dobles al reintentar.

El servidor debe almacenar y consultar las keys procesadas; requiere TTL o cleanup para no crecer indefinidamente.

34. Two-Phase Commit (2PC)

Protocolo para hacer transacciones atómicas entre múltiples bases de datos. Fase 1: el coordinador pregunta si pueden commitear. Fase 2: todos commitean o abortan.

Los participantes mantienen locks entre fases. Si el coordinador falla, el sistema queda bloqueado indefinidamente.

35. Saga Pattern

Alternativa a transacciones distribuidas: divide operaciones en transacciones locales con acciones compensatorias. Si un paso falla, los pasos anteriores se compensan (undo).

La lógica de compensación es compleja. El sistema es eventualmente consistente; pueden existir estados intermedios visibles para otros servicios.

36. Consistent Hashing Ring

Organiza valores hash en un anillo donde cada nodo es responsable de rangos. Los virtual nodes (múltiples posiciones por nodo físico) mejoran la distribución. Estándar en Redis Cluster y Cassandra.

Sin virtual nodes la distribución es desigual. La configuración de vnodes requiere tuning cuidadoso según la capacidad de cada nodo.

37. Clock Skew

Diferencias en los relojes entre máquinas a pesar de la sincronización NTP. Rompe la lógica de ordenamiento basada en timestamps wall-clock. Los sistemas usan relojes lógicos en su lugar.

Confiar en wall-clock time para ordenar eventos en sistemas distribuidos es un bug de diseño extremadamente común.

38. Vector Clock

Rastrea el ordenamiento causal de eventos sin relojes sincronizados. Cada nodo mantiene un contador; los mensajes incluyen el vector clock, permitiendo determinar causalidad en lugar de tiempo absoluto.

El tamaño del vector crece con el número de nodos, volviéndose costoso de mantener en sistemas con miles de nodos.

26. Distributed System

Multiple machines communicating over networks to achieve shared goals. Introduces unique challenges: network failures, partial failures, and consistency across data copies.

Distributed systems bring complexity that monoliths don't have; justify them with a real scale requirement.

27. CAP Theorem

A distributed system can guarantee only two of three: Consistency, Availability, Partition tolerance. Since partitions are inevitable, the real choice during failures is between C and A.

No system can be 100% consistent AND 100% available under simultaneous network partitions.

28. Strong Consistency

Every read reflects the latest write regardless of which node responds. Requires coordination before responding. Appropriate for financial data and critical inventory.

Coordination overhead reduces throughput and increases latency compared to eventual consistency.

29. Eventual Consistency

Replicas converge to the same state over time but may briefly differ. Cheaper and more available. Suitable for like counts, feeds, and recommendations.

Clients may temporarily read stale data; unacceptable for systems where precision is critical.

30. Consensus

Multiple nodes agree on a single value despite individual failures. Algorithms like Raft and Paxos require majority agreement, preventing split-brain scenarios.

Consensus is expensive in latency and network traffic; used selectively for critical decisions.

31. Leader Election

Distributed nodes agree which one coordinates work. Requires consensus to prevent dual leaders (split-brain). Used in distributed databases like etcd or task coordinators.

The window between a leader failing and a new one being elected temporarily reduces system capacity.

32. Idempotency

Operations that produce the same result whether executed once or multiple times. Distributed systems can't guarantee exactly-once delivery, making this essential for safe retries.

Implementing idempotency requires tracking already-executed operations, adding state management and storage overhead.

33. Idempotency Key

A unique client-generated identifier enabling server detection and rejection of duplicate requests. Standard in payment APIs (Stripe, PayPal) to prevent double charges on retries.

The server must store and query processed keys; requires TTL or cleanup to prevent unbounded growth.

34. Two-Phase Commit (2PC)

Protocol making transactions atomic across multiple databases. Phase 1: coordinator asks if participants can commit. Phase 2: all commit or abort together.

Participants hold locks between phases. If the coordinator crashes, the system blocks indefinitely.

35. Saga Pattern

Alternative to distributed transactions: breaks operations into local transactions with compensating actions. If a step fails, earlier steps are compensated (undone).

Compensation logic is complex. The system reaches eventual consistency; intermediate states can be visible to other services.

36. Consistent Hashing Ring

Arranges hash values in a ring where each node is responsible for ranges. Virtual nodes (multiple positions per physical node) improve distribution. Standard in Redis Cluster and Cassandra.

Without virtual nodes distribution is uneven. Vnode configuration requires careful tuning based on each node's capacity.

37. Clock Skew

Time differences between machine clocks despite NTP synchronization. Breaks timestamp-based ordering logic. Systems use logical clocks instead of wall-clock time.

Relying on wall-clock time to order events in distributed systems is an extremely common design bug.

38. Vector Clock

Tracks causal event ordering without synchronized clocks. Each node maintains a counter; messages include the vector clock, allowing causality (not just timing) to be determined.

The vector size grows with the number of nodes, becoming expensive to maintain in systems with thousands of nodes.

4. Mensajería y Comunicación

Seis conceptos que habilitan la comunicación asincrónica entre componentes y las funcionalidades en tiempo real.

4. Messaging & Communication

Six concepts enabling asynchronous communication between components and real-time features.

39. Message Queue

Retiene mensajes de productores hasta que los consumidores los procesen. Desacopla componentes temporalmente y absorbe picos de tráfico sin perder datos. Ejemplos: RabbitMQ, Amazon SQS.

Los resultados no están disponibles inmediatamente; no es adecuado para operaciones que requieren respuesta síncrona al cliente.

40. Pub/Sub

Múltiples suscriptores reciben copias de los mensajes publicados. A diferencia de las queues donde un solo consumidor maneja cada mensaje. Ideal cuando múltiples servicios reaccionan al mismo evento.

Si no hay suscriptores activos, los mensajes se pierden a menos que uses retención de log (como Apache Kafka).

41. Dead-Letter Queue (DLQ)

Retiene mensajes que fallaron después del límite de reintentos configurado. Previene que mensajes "venenosos" bloqueen la queue principal. Monitorearla es esencial para la salud del sistema.

Los mensajes en DLQ requieren intervención manual o automatización de diagnóstico; ignorarlos produce pérdida de datos silenciosa.

42. Backpressure

El consumidor señala al productor que reduzca la velocidad de envío cuando está sobrecargado. Sin backpressure, las queues crecen sin límite hasta agotar la memoria disponible.

Implementar backpressure requiere coordinación entre productor y consumidor; puede añadir latencia al pipeline de procesamiento.

43. WebSocket

Conexión bidireccional persistente entre cliente y servidor. Menor overhead que abrir conexiones HTTP repetidas. Esencial para chat en tiempo real, juegos multijugador y dashboards en vivo.

Requiere conexiones stateful y un pub/sub backplane para escalar horizontalmente entre múltiples instancias del servidor.

44. Server-Sent Events (SSE)

Streaming unidireccional del servidor al cliente sobre una conexión HTTP persistente. Más simple que WebSockets con reconexión automática incorporada. Ideal para notificaciones y streaming de respuestas de LLMs.

Solo funciona de servidor a cliente. Si necesitas comunicación bidireccional, WebSockets es la alternativa necesaria.

39. Message Queue

Holds messages from producers until consumers process them. Temporally decouples components and absorbs traffic spikes without data loss. Examples: RabbitMQ, Amazon SQS.

Results are not immediately available; not suitable for operations requiring a synchronous client response.

40. Pub/Sub

Multiple subscribers receive copies of published messages. Unlike queues where one consumer handles each message. Ideal when multiple services react to the same event.

If no active subscribers exist, messages are lost unless you use log retention (like Apache Kafka).

41. Dead-Letter Queue (DLQ)

Holds messages that failed after the configured retry limit. Prevents "poison" messages from blocking the main queue. Monitoring it is essential for system health.

Messages in DLQ require manual intervention or diagnostic automation; ignoring them causes silent data loss.

42. Backpressure

Consumer signals producer to slow down when overwhelmed. Without backpressure, queues grow without bound until the system runs out of memory.

Implementing backpressure requires coordination between producer and consumer; can add latency to the processing pipeline.

43. WebSocket

Persistent bidirectional connection between client and server. Lower overhead than repeated HTTP connections. Essential for real-time chat, multiplayer games, and live dashboards.

Requires stateful connections and a pub/sub backplane to scale horizontally across multiple server instances.

44. Server-Sent Events (SSE)

One-way streaming from server to client over a persistent HTTP connection. Simpler than WebSockets with built-in reconnection. Ideal for notifications and LLM response streaming.

Only works server-to-client. If you need bidirectional communication, WebSockets is the necessary alternative.

5. Confiabilidad y Conceptos Modernos

Los últimos seis conceptos: cómo mantener la disponibilidad bajo estrés extremo y cómo la IA se integra con la infraestructura moderna.

5. Reliability & Modern Concepts

The final six concepts: how to maintain availability under extreme stress and how AI integrates with modern infrastructure.

45. Circuit Breaker

Monitorea llamadas a dependencias y las detiene cuando la tasa de fallo supera un umbral. Tres estados: Closed (normal), Open (rechaza inmediatamente), Half-Open (prueba recuperación). Previene fallos en cascada.

Puede rechazar requests válidos durante la ventana "open". Requiere implementar una respuesta degradada o fallback explícito.

46. Rate Limiting

Limita los requests por cliente por período de tiempo. El algoritmo Token Bucket es el más común: el bucket se llena a tasa fija y se vacía con cada request. Protege de sobrecarga y abuso.

Clientes legítimos bajo picos de tráfico pueden ser bloqueados. Los límites deben comunicarse claramente con headers HTTP (Retry-After, X-RateLimit-*).

47. Load Shedding

Rechaza deliberadamente requests en exceso durante sobrecarga. "La disponibilidad parcial es mejor que el fallo total": servir el 80% bien es mejor que intentar todos y fallar todos.

Decidir cuáles requests rechazar requiere priorización inteligente; rechazar los incorrectos puede romper SLAs críticos.

48. Bloom Filter

Probador probabilístico de membresía eficiente en espacio. Puede confirmar con certeza que un elemento NO está en el conjunto; puede falsamente afirmar que SÍ está (false positive, nunca false negative).

Los false positives son aceptables solo cuando el costo de procesarlos es bajo. Las implementaciones básicas no soportan eliminaciones.

49. Embedding

Representaciones vectoriales numéricas que capturan el significado semántico de texto o imágenes. Elementos similares tienen vectores próximos en el espacio vectorial. Base de la búsqueda semántica moderna.

Los embeddings grandes (1536+ dimensiones) son costosos de almacenar y buscar; requieren bases de datos vectoriales especializadas como Pinecone o pgvector.

50. RAG (Retrieval-Augmented Generation)

Arquitectura de LLM que recupera conocimiento externo relevante como contexto en tiempo de query. Dos fases: ingestión (docs→chunks→embeddings→vector DB) y retrieval (busca contexto relevante para fundamentar la respuesta).

La calidad del chunking y la estrategia de retrieval determinan el 80% de la calidad del sistema. No es una solución plug-and-play.

45. Circuit Breaker

Monitors dependency calls and stops them when the failure rate exceeds a threshold. Three states: Closed (normal), Open (reject immediately), Half-Open (test recovery). Prevents cascading failures.

May reject valid requests during the "open" window. Requires implementing a degraded response or explicit fallback strategy.

46. Rate Limiting

Caps requests per client per time period. The Token Bucket algorithm is most common: the bucket fills at a fixed rate and empties with each request. Protects against overload and abuse.

Legitimate clients under traffic spikes may be blocked. Limits must be communicated clearly via HTTP headers (Retry-After, X-RateLimit-*).

47. Load Shedding

Deliberately rejects excess requests during overload. "Partial availability beats total failure": serving 80% well beats attempting all requests and failing all of them.

Deciding which requests to reject requires smart prioritization; rejecting the wrong ones can break critical SLAs.

48. Bloom Filter

Space-efficient probabilistic membership tester. Can confirm with certainty that an item is NOT in the set; may falsely claim it IS (false positives only, never false negatives).

False positives are acceptable only when their processing cost is low. Basic implementations don't support deletions.

49. Embedding

Numerical vector representations capturing the semantic meaning of text or images. Similar items have proximate vectors in vector space. Foundation of modern semantic search.

Large embeddings (1536+ dimensions) are expensive to store and search; require specialized vector databases like Pinecone or pgvector.

50. RAG (Retrieval-Augmented Generation)

LLM architecture that retrieves relevant external knowledge as context at query time. Two phases: ingestion (docs→chunks→embeddings→vector DB) and retrieval (finds relevant context to ground the response).

The quality of chunking and retrieval strategy determines 80% of system quality. It is not a plug-and-play solution.

Conclusión

Estos 50 conceptos no son un checklist que debes implementar — son un vocabulario. El valor real está en saber cuándo aplicar cada uno y, más importante, cuándo no aplicarlo. Un sistema sobrediseñado con consistent hashing, 2PC y vector clocks para 100 usuarios es tan problemático como uno subdiseñado que colapsa bajo carga real.

La arquitectura no es sobre patrones. Es sobre trade-offs deliberados en función del problema real que tienes hoy.

La próxima vez que diseñes un sistema, pregúntate: ¿cuál es el trade-off que estoy aceptando con esta decisión, y vale la pena? Esa pregunta es la diferencia entre un arquitecto que conoce los conceptos y uno que sabe diseñar sistemas reales.

Conclusion

These 50 concepts are not a checklist to implement — they are a vocabulary. The real value lies in knowing when to apply each one and, more importantly, when not to. An over-engineered system with consistent hashing, 2PC, and vector clocks for 100 users is just as problematic as an under-engineered one that collapses under real load.

Architecture is not about patterns. It's about deliberate trade-offs based on the real problem you have today.

The next time you design a system, ask yourself: what trade-off am I accepting with this decision, and is it worth it? That question is the difference between an architect who knows the concepts and one who knows how to design real systems.
