SDLC Toolkit: A Full Development Pipeline with Claude

How a plugin turns an idea into code-ready specs — PRD, architecture, ATAM evaluation, functional and technical specs, test strategy and deployment, all orchestrated across 8 stages.

July 2026 Felipe Pabón

El problema que quería resolver

Cada vez que arranca un proyecto de software, el equipo repite el mismo ciclo: conversaciones dispersas sobre el producto, un PRD incompleto, una arquitectura que vive en la cabeza del tech lead, specs funcionales que nadie actualiza y documentos técnicos que quedan obsoletos al tercer sprint. El conocimiento se fragmenta, las decisiones se toman sin contexto y los desarrolladores empiezan a codear sin una base sólida.

Llevo tiempo trabajando con Claude Code y viendo cómo los skills pueden cambiar la forma de trabajar. La pregunta natural fue: ¿qué pasa si el proceso de discovery y diseño completo — no solo una parte — se convierte en un pipeline orquestado?

Así nació el SDLC Toolkit: un plugin de Claude que guía un proyecto desde la idea inicial hasta las specs listas para implementar, siguiendo estándares de arquitectura limpia, seguridad y buenas prácticas de React y Go.

The problem I wanted to solve

Every time a software project kicks off, the team repeats the same cycle: scattered product conversations, an incomplete PRD, an architecture that lives only in the tech lead's head, functional specs nobody updates, and technical documents that are obsolete by the third sprint. Knowledge fragments, decisions get made without context, and developers start coding without a solid foundation.

I've been working with Claude Code for a while, watching how skills can change the way teams work. The natural question arose: what if the entire discovery and design process — not just one piece — became an orchestrated pipeline?

That's how the SDLC Toolkit was born: a Claude plugin that guides a project from initial idea to implementation-ready specs, following clean architecture standards, security rules, and React/Go best practices.

Cómo funciona el toolkit

El plugin expone un skill maestro, el sdlc-orchestrator, que actúa como punto de entrada para cualquier proyecto. Al invocarlo, Claude te hace tres preguntas clave — nombre del proyecto, descripción breve y stakeholders — y luego presenta el pipeline completo con sus 8 etapas.

Cada etapa es un skill especializado que sabe exactamente qué necesita de la etapa anterior y qué produce para la siguiente. El orchestrator mantiene el estado del pipeline y te permite avanzar secuencialmente o saltar a cualquier etapa si ya tienes parte del trabajo hecho.

"Start a new project to build an online marketplace" — Claude recoge contexto, genera el PRD, guía la arquitectura arc42, corre el análisis ATAM, produce las specs funcionales y técnicas, diseña la estrategia de tests y genera las specs de despliegue. Todo en una sesión.

Lo interesante no es que Claude "haga las cosas" — es que cada skill sabe a qué estándar atenerse. Los skills de technical specs consultan automáticamente cuatro referencias compartidas:

  • security-rules.md — OWASP Top 10, JWT, validación de inputs, manejo de secretos
  • clean-architecture.md — separación de capas, inyección de dependencias, patrones
  • react-standards.md — TypeScript, Atomic Design, React Query, WCAG 2.1 AA
  • golang-standards.md — package structure, middleware, error handling explícito, zerolog

El resultado son specs que un desarrollador puede tomar y empezar a codear sin tener que adivinar decisiones de arquitectura ni recordar las reglas de seguridad del equipo.

How the toolkit works

The plugin exposes a master skill, the sdlc-orchestrator, which acts as the entry point for any project. When invoked, Claude asks three key questions — project name, brief description, and stakeholders — and then presents the full pipeline with its 8 stages.

Each stage is a specialized skill that knows exactly what it needs from the previous stage and what it produces for the next. The orchestrator maintains pipeline state and lets you advance sequentially or jump to any stage if you already have some work done.

"Start a new project to build an online marketplace" — Claude collects context, generates the PRD, guides arc42 architecture, runs the ATAM analysis, produces functional and technical specs, designs the test strategy, and generates deployment specs. All in one session.

The interesting part isn't that Claude "does things" — it's that each skill knows which standard to follow. The technical specs skills automatically consult four shared references:

  • security-rules.md — OWASP Top 10, JWT, input validation, secrets management
  • clean-architecture.md — layer separation, dependency injection, design patterns
  • react-standards.md — TypeScript, Atomic Design, React Query, WCAG 2.1 AA
  • golang-standards.md — package structure, middleware, explicit error handling, zerolog

The result is specs a developer can pick up and start coding from — without having to guess architectural decisions or remember the team's security rules.

Las 8 etapas en detalle

Cada etapa del pipeline tiene un propósito preciso y un output concreto. Aquí un resumen de lo que produce cada una:

1. Product Design: Genera el PRD completo — visión del producto, personas de usuario (2-3), epics y features priorizados (P0/P1/P2), user stories en formato "As [role], I want [action], so that [benefit]", KPIs y restricciones.

2. Architecture (arc42): Documenta la arquitectura siguiendo el estándar arc42 del SEI — contexto del sistema, decisiones arquitectónicas (ADRs), vista de componentes, vista de despliegue, conceptos transversales (logging, seguridad, cache).

3. ATAM Evaluation: Analiza los tradeoffs de la arquitectura usando el método ATAM — escenarios de calidad, árboles de utilidad, sensitivity points y tradeoff points. Identifica riesgos arquitectónicos antes de empezar a construir.

4. Architecture Review: Evalúa el documento arc42, puntúa cada dimensión e identifica gaps. Produce un reporte con recomendaciones Must Have / Nice to Have, listo para compartir con stakeholders.

5. Functional Specs: Detalla cada feature con flujos principales y alternativos, criterios de aceptación en Gherkin, wireframes SVG inline, reglas de negocio y dependencias de API.

6. Technical Specs: Genera los contratos técnicos listos para código — OpenAPI YAML para los endpoints, estructura de componentes React con Atomic Design, arquitectura del microservicio Go con las capas domain/application/infrastructure/interface, schemas de base de datos y checklist de seguridad.

7. Test Strategy: Define la estrategia de testing completa — pirámide de tests (unitarios, integración, E2E), smoke tests para validar el despliegue, cobertura mínima por capa y fixtures de datos de prueba.

8. Deployment Specs: Diseña la infraestructura en Azure/AWS/GCP — recursos necesarios, configuración de CI/CD, variables de entorno, estrategia de rollout y runbook de despliegue inicial.

The 8 stages in detail

Each pipeline stage has a precise purpose and a concrete output. Here's a summary of what each one produces:

1. Product Design: Generates the complete PRD — product vision, user personas (2-3), prioritized epics and features (P0/P1/P2), user stories in "As [role], I want [action], so that [benefit]" format, KPIs, and constraints.

2. Architecture (arc42): Documents the architecture following the SEI's arc42 standard — system context, architectural decisions (ADRs), component view, deployment view, cross-cutting concerns (logging, security, cache).

3. ATAM Evaluation: Analyzes architectural trade-offs using the ATAM method — quality scenarios, utility trees, sensitivity points, and tradeoff points. Identifies architectural risks before you start building.

4. Architecture Review: Evaluates the arc42 document, scores each dimension, and identifies gaps. Produces a report with Must Have / Nice to Have recommendations, ready to share with stakeholders.

5. Functional Specs: Details each feature with main and alternative flows, Gherkin acceptance criteria, inline SVG wireframes, business rules, and API dependencies.

6. Technical Specs: Generates code-ready technical contracts — OpenAPI YAML for endpoints, React component structures with Atomic Design, Go microservice architecture with domain/application/infrastructure/interface layers, database schemas, and security checklists.

7. Test Strategy: Defines the complete testing strategy — test pyramid (unit, integration, E2E), smoke tests to validate deployment, minimum coverage per layer, and test data fixtures.

8. Deployment Specs: Designs the infrastructure on Azure/AWS/GCP — required resources, CI/CD configuration, environment variables, rollout strategy, and initial deployment runbook.

Lo que aprendí construyendo esto

Construir este toolkit enseña cosas que no son obvias cuando empiezas a trabajar con skills de Claude.

La primera lección es que los estándares compartidos son la clave de la consistencia. Si cada skill tiene sus propias reglas de seguridad o sus propias convenciones de arquitectura, los outputs son inconsistentes y no se pueden encadenar. Los cuatro archivos de referencias (security, clean-arch, react, golang) actúan como la "constitución" del toolkit — todos los skills la leen, todos los outputs la respetan.

La segunda lección es que la flexibilidad vale más que el orden estricto. El pipeline es secuencial por diseño, pero el orchestrator permite saltar etapas. Si ya tienes un PRD aprobado, empiezas en la etapa 2. Si solo necesitas las specs técnicas de un feature, invocas ese skill directamente. El usuario sabe más que el pipeline sobre dónde está parado.

La tercera es que el modelo mental importa más que la herramienta. El SDLC Toolkit no reemplaza al equipo de producto ni al arquitecto — los amplifica. Un PM puede ir de "tengo una idea" a "tengo un PRD estructurado con personas y KPIs" en minutos. Un arquitecto puede detectar tradeoffs críticos en su diseño sin esperar al architecture review formal. La velocidad cambia el juego.

What I learned building this

Building this toolkit teaches things that aren't obvious when you first start working with Claude skills.

The first lesson: shared standards are the key to consistency. If each skill has its own security rules or its own architecture conventions, the outputs are inconsistent and can't be chained together. The four reference files (security, clean-arch, react, golang) act as the toolkit's "constitution" — all skills read it, all outputs respect it.

The second lesson: flexibility is worth more than strict ordering. The pipeline is sequential by design, but the orchestrator lets you skip stages. If you already have an approved PRD, start at stage 2. If you only need technical specs for one feature, invoke that skill directly. The user knows more than the pipeline about where they're standing.

The third: the mental model matters more than the tool. The SDLC Toolkit doesn't replace the product team or the architect — it amplifies them. A PM can go from "I have an idea" to "I have a structured PRD with personas and KPIs" in minutes. An architect can detect critical trade-offs in their design without waiting for the formal architecture review. The velocity shift is game-changing.

Más allá del pipeline: skills complementarios

Al completar las 8 etapas, el orchestrator ofrece cinco skills adicionales pensados para acelerar la implementación y operar el sistema de forma segura en producción:

database-schema — Genera esquemas SQL production-ready con UUID como primary keys, timestamps en todas las tablas, scripts de migración con golang-migrate (forward-only), estrategia de índices y datos de seed. Ideal si el backend tiene una capa de persistencia no trivial.

implementation-scaffolding — Genera la estructura base del proyecto lista para codear. Para Go, sigue clean-architecture (cmd/ → internal/domain/application/infrastructure/interface/). Para React, pregunta la estructura preferida (Atomic Design, Feature-Based, Page-Based o Flat) y genera el árbol de directorios, archivos de configuración y stubs de componentes.

observability-specs — Define la estrategia completa de observabilidad: logging estructurado con zerolog (zero PII), métricas con Prometheus/CloudWatch/Azure Monitor, alertas con thresholds, dashboards en Grafana/Azure, SLO/SLI targets y distributed tracing con OpenTelemetry.

security-validation — Valida specs, código y configuraciones contra OWASP Top 10. Produce un reporte de vulnerabilidades con sugerencias de fix y un compliance checklist. Se puede invocar en cualquier etapa del pipeline, no solo al final.

harness-setup — Genera el CLAUDE.md y hooks de seguridad pre-configurados para que los equipos deleguen trabajo a Claude Code de forma controlada y auditable: protege carpetas críticas, enforza las convenciones del proyecto, verifica tests antes de commits y define cuándo el agente debe detenerse a preguntar.

Estos cinco skills también se pueden invocar de forma completamente independiente, sin necesidad de haber corrido el pipeline completo.

Beyond the pipeline: complementary skills

Once the 8 stages are complete, the orchestrator offers five additional skills designed to accelerate implementation and operate the system safely in production:

database-schema — Generates production-ready SQL schemas with UUIDs as primary keys, timestamps on all tables, golang-migrate migration scripts (forward-only), index strategy, and seed data. Ideal when the backend has a non-trivial persistence layer.

implementation-scaffolding — Generates the base project structure ready to code. For Go, it follows clean-architecture (cmd/ → internal/domain/application/infrastructure/interface/). For React, it asks your preferred structure (Atomic Design, Feature-Based, Page-Based, or Flat) and generates the directory tree, config files, and component stubs.

observability-specs — Defines the complete observability strategy: structured logging with zerolog (zero PII), metrics with Prometheus/CloudWatch/Azure Monitor, alerts with thresholds, Grafana/Azure dashboards, SLO/SLI targets, and distributed tracing with OpenTelemetry.

security-validation — Validates specs, code, and configurations against OWASP Top 10. Produces a vulnerability report with fix suggestions and a compliance checklist. Can be invoked at any pipeline stage, not just at the end.

harness-setup — Generates the CLAUDE.md and pre-configured security hooks so teams can delegate work to Claude Code in a controlled, auditable way: protects critical folders, enforces project conventions, verifies tests before commits, and defines when the agent should stop and ask.

These five skills can also be invoked completely independently, without having run the full pipeline first.

Cómo instalarlo y usarlo

El toolkit está publicado como plugin de Claude en GitHub. Para instalarlo en Claude Code:

claude plugins add https://github.com/fepc18/claude-skills/tree/main/sdlc-toolkit

Una vez instalado, basta con escribir:

sdlc

...y el orchestrator toma el control. También puedes invocar skills individuales directamente con sus frases de activación: crear un PRD, specs técnicas del servicio de pagos, estrategia de testing.

El repo de ejemplos en github.com/fepc18/sdlc-toolkit-examples tiene outputs reales de proyectos de ejemplo — un buen punto de partida para entender qué produce cada etapa.

Si lo usas y tienes feedback, abre un issue en el repo o escríbeme en LinkedIn. Estoy iterando activamente sobre el toolkit.
